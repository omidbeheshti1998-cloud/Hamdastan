# فلو احراز هویت و ورود

مسیر: `/` (ریشهٔ اپ) — کل فلو در یک صفحه و با یک ماشین حالت سمت کلاینت اجرا می‌شود،
تا «بازگشت» اطلاعات واردشده را از دست ندهد و جابه‌جایی بین مراحل بدون رفت‌وبرگشت
به سرور باشد.

> **وضعیت فعلی: فقط UI.** تماس‌های سرور هنوز Mock هستند. بخش
> [اتصال به بک‌اند](#اتصال-به-بک‌اند) را قبل از production بخوان.

```
STEP 1 — شماره موبایل
        │
        ├── حساب وجود ندارد ──▶ STEP 2A — نام و نام خانوادگی
        │                              │
        │                              ▼
        │                       STEP 3 — علایق
        │                              │
        │                              ▼
        │                       کوییز ترجیحات
        │                              │
        │                              ▼
        │                       مرحلهٔ آخر — پروفایل ──▶ حساب ساخته شد
        │
        └── حساب وجود دارد ───▶ STEP 2B — کد تأیید (OTP) ──▶ ورود موفق
```

مرحله‌های علایق، ترجیحات و پروفایل فقط در مسیر ثبت‌نام هستند، نه در ورود.
جزئیاتشان در [`docs/ONBOARDING.md`](./ONBOARDING.md)،
[`docs/PREFERENCES.md`](./PREFERENCES.md) و [`docs/PROFILE.md`](./PROFILE.md).

## قواعد رفتاری

### شماره موبایل

`lib/auth/mobile.ts` تنها مرجع اعتبارسنجی است.

- الگوی معتبر: `^09\d{9}$`
- ارقام فارسی (`۰۹…`) و عربی (`٠٩…`) خودکار به لاتین تبدیل می‌شوند.
- فرم‌های `+98…` و `0098…` و `9…` پذیرفته و نرمال می‌شوند، اما **فقط وقتی تعداد
  ارقام کامل شده باشد** — تا تایپ کردن وسط کار پرش نکند.
- نمایش ماسک‌شده: `09123456789` → `0912 *** 6789`

### کد تأیید

- ۶ رقم، فقط عدد.
- اعتبار **۲ دقیقه**. مرجع زمان `Date.now()` مطلق است، نه شمارش تیک، تا تب
  پس‌زمینه تایمر را منحرف نکند.
- تأیید پس از وارد شدن رقم ششم **خودکار** انجام می‌شود؛ دکمهٔ submit ندارد.
- پشتیبانی از Paste و AutoFill سیستم‌عامل (`autocomplete="one-time-code"`).
- تا پایان تایمر، «ارسال مجدد» غیرفعال است و زمان باقی‌مانده را نشان می‌دهد.
- با ارسال مجدد: کد قبلی باطل، ورودی پاک، فوکوس به خانهٔ اول، تایمر از `02:00`.

#### حالت‌های خطا

| حالت | پیام | اکشن |
|---|---|---|
| کد اشتباه | «کد واردشده صحیح نیست.» | خانه‌ها قرمز، قابل اصلاح |
| منقضی | «اعتبار این کد تمام شده است. کد جدید دریافت کنید.» | «ارسال مجدد کد» |
| خطای شبکه | «ارتباط با سرور برقرار نشد. دوباره تلاش کنید.» | «تلاش مجدد» |

کد منقضی حتی اگر درست باشد سمت کلاینت هم رد می‌شود (`Date.now() >= expiresAt`)،
تا یک درخواست بی‌فایده به سرور نرود. اعتبارسنجی نهایی همچنان وظیفهٔ سرور است.

**انقضا بر هر خطای قبلی مقدم است.** اگر کد وسطِ نمایش «کد واردشده صحیح نیست.»
منقضی شود، آن پیام دیگر درست نیست و کاربر را گمراه می‌کند؛ پس هم پیام و هم اکشن
و هم حالت قرمز خانه‌ها به حالت «منقضی / ارسال مجدد» سوییچ می‌کنند
(`shownError` در `otp-step.tsx`).

### جلوگیری از Double Submit

دو لایه دارد و هر دو لازم است:

1. `PrimaryButton` در حالت `loading` خودش را disable می‌کند.
2. `OtpStep` یک `useRef` به‌نام `inFlight` دارد، چون auto-verify می‌تواند هم‌زمان
   با کلیک کاربر شلیک شود و `useState` به‌موقع به‌روز نمی‌شود.

## تست دستی در حالت Mock

`lib/auth/client.ts` رفتار سرور را شبیه‌سازی می‌کند (تأخیر ۷۰۰ms):

| ورودی | نتیجه |
|---|---|
| `09050466960` (تنها شمارهٔ «موجود») | کاربر موجود → مسیر OTP |
| هر شمارهٔ معتبر دیگری | کاربر جدید → مسیر ثبت‌نام |
| کد `123456` | تأیید موفق |
| هر کد دیگر | «کد واردشده صحیح نیست.» |
| کد `000000` | شبیه‌سازی خطای شبکه |

## اتصال به بک‌اند

**قاعدهٔ معماری:** فرانت فقط به بک‌اند داخلی (Route Handler های همین اپ) درخواست
می‌دهد. تماس با سرویس خارجی وظیفهٔ بک‌اند است و هرگز از مرورگر انجام نمی‌شود.

```
کامپوننت‌ها ──▶ lib/auth/client.ts ──▶ /api/auth/… (Route Handler) ──▶ سرویس خارجی
```

`lib/auth/client.ts` تنها نقطهٔ تماس با سرور است. برای اتصال واقعی فقط بدنهٔ
همین توابع عوض می‌شود و هیچ کامپوننتی تغییر نمی‌کند:

| تابع | مسیر داخلی موردنظر |
|---|---|
| `checkMobile` | `POST /api/auth/check-mobile` |
| `sendOtp` | `POST /api/auth/otp/send` |
| `verifyOtp` | `POST /api/auth/otp/verify` |
| `register` | `POST /api/auth/register` |
| `saveInterests` | `POST /api/onboarding/interests` |
| `savePreferences` | `POST /api/onboarding/preferences` |
| `checkUsername` | `GET /api/profile/username-available` |
| `saveProfile` | `POST /api/profile` |

هنگام پیاده‌سازی بک‌اند این‌ها را در نظر بگیر:

- خطای شبکه/سرور باید `AuthNetworkError` پرتاب کند تا UI پیام درست را نشان دهد.
  نتیجهٔ «کد اشتباه» خطا نیست و با `{ ok: false }` برمی‌گردد.
- ارسال مجدد باید کد قبلی را **بلافاصله** باطل کند.
- اعتبار ۲ دقیقه باید سمت سرور هم اعمال شود؛ تایمر کلاینت فقط UI است.
- Rate limit روی ارسال و بررسی کد لازم است (کلاینت فقط تایمر UI دارد).
- شماره را همیشه نرمال‌شده (`09xxxxxxxxx`) بفرست — `normalizeMobile` این را تضمین می‌کند.
- نشست پس از ورود موفق باید با کوکی `httpOnly` ست شود، نه در `localStorage`.

### دیتابیس

هیچ اسکیمایی در این تغییر ساخته یا مهاجرت نشده است. هر تغییر دیتابیسی باید
به‌صورت کوئری برای اجرا به صاحب پروژه داده شود.

## RTL

قواعد کلی در [`docs/RTL.md`](./RTL.md) است. دو نکتهٔ خاص این فلو:

- کانتینر خانه‌های OTP و فیلد شماره موبایل عمداً `dir="ltr"` / کلاس `.ltr` دارند،
  چون عدد همیشه چپ‌به‌راست خوانده می‌شود. Chrome خودش روی `input[type="tel"]`
  همین کار را می‌کند؛ کلاس `.ltr` فقط آن را در بقیهٔ مرورگرها هم قطعی می‌کند.
- عددی که وسط متن فارسی می‌نشیند (تایمر) با `flex gap-1` جدا شده تا bidi به‌هم نریزد.
